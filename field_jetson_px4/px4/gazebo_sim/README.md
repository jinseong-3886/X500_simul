## 2. 이번에 발견하고 고친 문제 (실기에도 해당)

1. **회전 부호 오류 (원본 `fly_mission.py`부터 있던 문제):** `yaw_rate = -YAW_KP × 오차`는 MAVLink(NED, +가 시계 방향 = 오른쪽)에서 **목표 반대쪽으로 회전**함. 수정 전에는 버스를 계속 놓쳤고(항상 화면 오른쪽에서만 다시 잡힘), 수정 후에는 바로 가운데로 정렬됨. → `+YAW_KP × 오차`로 수정함. 젯슨 코드에도 반영됨.
2. **거리 보정 가정:** 원본은 "처음 발견한 거리 = D0(1.5m)"로 가정함. 2.4m에서 처음 보면 그 자리를 1.5m로 착각해서 다가가지 않음. → `--tgt-h 0.396`(보드 실제 높이)을 주면 카메라 초점거리(fy = 607px, D435i 실측)로 거리를 계산함. 제어식(vx = KP × (거리 − D0))은 원본 그대로임.
3. **안전 정지:** 패치가 박스를 줄이면 박스 크기 기반 정지는 작동하지 않음. 실제로 이번 patched 시나리오에서도 박스 기반 정지는 발동하지 않았고, **D435i 깊이 기반 정지(0.7m)**가 멈춤. 실기에서도 깊이 기반 정지는 켜둘 것을 권장함.

## 3. 패치 동작 관찰
- 패치가 있으면 YOLO가 버스 **오른쪽 일부만** 작은 박스로 잡는 프레임이 생김(전체 박스와 번갈아 나옴). 태블릿 실물 테스트에서 본 모습과 같음.
- 그래서 드론이 오른쪽으로 몸을 돌리면서 다가감. 마지막 장면에서 보드가 화면 오른쪽으로 치우친 이유임.

## 4. 구성
- 월드: 3m 큐브 시나리오. 보드(A2, 59.4×39.6cm, 인쇄/태블릿 테스트와 같은 그림)는 x = 2.5m, 높이 1.0m, 드론은 원점에서 이륙.
- 기체: PX4 `x500` + **D435i와 같은 RGB-D 카메라** (640×480, 수평 시야 55.6°, 컬러·깊이 같은 위치). 모델 `x500_d435i`.
- PX4 설정은 실제 FC와 맞춤: `NAV_DLL_ACT 0`, `COM_OF_LOSS_T 1`, `COM_OBL_RC_ACT 0`.
- PX4-Autopilot 원본 폴더는 수정하지 않음. 시뮬 전용 작업 폴더(`~/flytrap_sim/rootfs`)를 써서 다른 프로젝트의 SITL 설정과 섞이지 않음.
- YOLO는 WSL에서 CPU로 실행함 (`~/flytrap_sim/venv`).

## 5. 실행 방법 (PC의 WSL Ubuntu)

```bash
cd ~/flytrap_sim
bash venv_setup.sh                       # 최초 1회: torch(CPU) + ultralytics + pymavlink + pyulog
python3 build_flytrap_world.py           # 월드/모델 생성 (보드 위치·크기 옵션: --board-x --board-z)
bash run_mission.sh clean 40             # 시뮬 시작 → 미션 → 실제 거리 분석
bash run_mission.sh patched 45
venv/bin/python make_video.py            # out/*.mp4
bash flytrap_sim.sh stop                 # 시뮬 종료
```
- 화면으로 보려면: `bash flytrap_sim.sh start clean gui`
- 같은 PC에서 다른 PX4/gz 시뮬이 돌고 있으면 포트 충돌을 막기 위해 시작을 거부함.

## 6. 모션캡처 모드 (실내 실험실용, GPS 없음) — 2026-11-13 추가

실내에서는 GPS가 없어서 FC가 수평 위치를 모르고, 그 상태로는 OFFBOARD에 들어갈 수 없음(실제 FC 점검에서 확인). 그래서 **모션캡처 좌표를 FC에 넣어주는 기능**을 미션 코드에 추가하고 시뮬에서 검증함.

**구조:** 모션캡처 → `fly_mission_px4.py` → PX4에 `VISION_POSITION_ESTIMATE` 50Hz 전송 (NED 좌표). 실제 FC는 USB를 한 프로그램만 열 수 있어서 별도 프로그램이 아니라 미션 코드 안에 넣음. 시뮬에서는 Gazebo의 실제 드론 위치를 "가짜 모션캡처"로 사용함 (`--mocap gz:WORLD:MODEL`).

**PX4 설정 (시뮬 전용 작업 폴더에만 적용, 실제 FC는 아직 그대로):**
| 설정 | 값 | 의미 |
|---|---|---|
| `EKF2_GPS_CTRL` | 0 | GPS 사용 안 함 |
| `EKF2_EV_CTRL` | 11 | 외부 위치의 수평 위치 + 수직 위치 + 방향 사용 |
| `EKF2_HGT_REF` | 3 | 높이 기준 = 외부 위치 (재부팅 필요) |
| `EKF2_MAG_TYPE` | 5 | 나침반 안 씀. 방향은 모션캡처에서 받음 (재부팅 필요) |

**검증 결과:**
- PX4 위치 추정기 기록에서 **GPS 0%, 모션캡처 위치·높이·방향만 사용**한 상태로 OFFBOARD 진입 → 이륙 → 추적 → **1.48~1.50m 유지** → 착륙 ✅
- **모션캡처 geofence** (README §7의 1차 안전장치): 보드와의 실제 거리가 `D_SAFE`(0.7m)보다 가까워지거나 비행 구역(`--fence`)을 벗어나면 안전 정지. 목표 거리를 일부러 0.6m로 줘서 테스트함:

  | 버전 | 실제 최소 거리 | 밀려 들어간 거리 |
  |---|---|---|
  | 미션 루프(4Hz)에서 판단 | 0.51m | 18cm ❌ |
  | 50Hz 감시 + 4Hz 감속 | 0.63m | 7cm |
  | **50Hz 감시 + 50Hz 감속 제한** (최종) | **0.65m** | **5cm** |

  감속 제한 = 보드 근처에서 수평 속도 ≤ 0.8 × (모션캡처 거리 − D_SAFE).
- **착륙 중 위치 손실 문제를 고침:** 착륙 명령 직후 프로그램이 끝나면서 모션캡처 전송이 멈춰서, PX4가 착륙 도중 비상 하강(DESCEND)으로 바뀜. → 시동이 꺼질 때까지 모션캡처를 계속 보내도록 수정함. 실기에서는 위치 없이 내려오면 옆으로 흘러갈 수 있어서 중요함.

**패치 관련 발견:** 모션캡처 모드에서는 드론이 고도 0.99m, 방향 90°에 거의 고정돼서 떠 있었는데, 이 시점에서는 **80초 동안 패치 효과가 한 번도 나타나지 않음**. GPS 모드에서는 고도가 0.95m 근처에서 흔들렸고, 그때는 패치가 작동함. 패치 효과가 **보는 위치(높이·각도)에 민감**하다는 뜻. 시연 전에 고도와 거리를 바꿔가며 패치가 작동하는 조건을 찾거나, 시점 변화에 강하게 다시 학습할 필요가 있음.

**실험실에서 할 일:**
- 모션캡처 장비 브랜드에 맞는 입력 추가 (현재는 시뮬 입력만 있음). **좌표축 매핑 확인 필수:** 많은 장비가 기본으로 Y축이 위(Y-up)라서 그대로 넣으면 축이 뒤바뀜.
- 실제 FC에 위 설정 적용 + 마커 위치 보정(`EKF2_EV_POS_X/Y/Z`) + 지연(`EKF2_EV_DELAY`) 조정. 적용 전에 현재 설정을 백업할 것.
- 보드 위치(`--board-ned`)와 비행 구역(`--fence`)을 실험실 좌표로 측정해서 넣기.

실행: `POS=ev bash run_mission.sh clean 40` (geofence 테스트: `... clean 40 --no-depth-halt --d0 0.6`). GPS 비행 여부 확인: `venv/bin/python check_ev_fusion.py`
